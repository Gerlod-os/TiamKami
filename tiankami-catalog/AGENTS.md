## 📋 ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА

### Логика работы

- **Проверяй информацию по коду**, не доверяй чужим отчётам.
- **Лечи корень проблемы**, а не симптомы.
- **Перед изменением логики** — опиши план (2–4 пункта) и получи согласие.
- **Не предлагай изменения, которых нет в коде**.
- **Не копируй весь проект в ответ** — ссылайся на файлы.
- **Не оставляй заглушек** в коде.
- **Если задача не решилась с двух попыток** — прекрати и предложи поискать решение.

### Откат изменений (Git)

- **Перед серьёзной правкой** создай страховочный коммит: `git add . && git commit -m "страховка перед изменениями"`.
- Сообщи пользователю простую команду-страховку: «Если что-то сломалось — я откачу через `git restore .`».
- **Если правка сломала код** — не исправляй множественными мелкими правками. Откати: `git restore .`, затем разберись в причине и начни заново другим подходом.

### Ресурсы Mac (8 ГБ RAM)

- Не запускай тяжёлые команды параллельно (одновременные `npm run build` и `npm run dev` не нужны).
- Не работай над одной задачей в двух AI-агентах одновременно — это лишняя нагрузка на память.
- Не сканируй проект заново без необходимости — используй собранные данные и кэш проверок.

### Работа с файлами

- **Используй `edit`** вместо создания новых файлов, где это возможно.

### Выполнение команд

- **ВСЕГДА покажи команду перед выполнением** и объясни её простыми словами.
- Команды из разрешённого списка `.clinerules` (`npm run dev`, `npm run build`, `npm run sync`, `npx prettier --write .`, `git status`, `git diff`) можно запускать без подтверждения.
- **Любые другие команды — только после подтверждения пользователя.**
- Не выполняй интерактивные команды (те, что ждут ввода с клавиатуры).

### План-режим (Plan Mode)

- Если пользователь работает в план-режиме (вкладка «План») — НИЧЕГО не меняй и не запускай команд, которые создают/записывают/удаляют.
- Только чтение, поиск, анализ. В конце ответа — план изменений и вопрос о согласии.
- Выход из план-режима делает только сам пользователь (переключает вкладку в Act mode).

### Взаимодействие с пользователем

- **Пользователь не программист** — объясняй логику простым языком.
- **Перед каждой командой** пиши, что она делает.
- **После каждого ответа** (для сложных задач) указывай:
  - `🎯 Задача:` — одно предложение
  - `📋 План:` — 2–4 пункта
- **Проверку в браузере делает пользователь** (DevTools, внешний вид). Не пиши «проверил в браузере», если этого не делал: запусти `npm run dev` и сообщи адрес для проверки.

## 🛠️ КОМАНДЫ ПРОЕКТА

```bash
npm run dev    # разработка (localhost:5173)
npm run build  # сборка: npm run sync → vite build → prerender (данные обновляются автоматически)
npm run sync   # скачать таблицу в src/data/*.json
npm run lint   # oxlint — линтер ошибок (НЕ ESLint)
npm test       # тесты vitest (3 файла, 49 тестов в __tests__)
```

**Сборка:** `npm run build` автоматически запускает `npm run sync` перед сборкой (prebuild hook).

**После изменений логики:** `npm run build` + `npx oxlint` + `npm test` + проверка `src/data/*.json`.
**После изменений данных:** `npm run sync` + проверка `src/data/*.json`.

## 📊 СТРУКТУРА ДАННЫХ (КЛЮЧЕВЫЕ МОМЕНТЫ)

- Мастер-таблица Google — ID в `src/config/dataSources.js`.
- Лист «Все рогалики» — TSV, ~440 строк.
- Лист «Подборки от Тиана» — парсер **ПОСТРОЧНЫЙ** (никогда не переписывай на колоночный).
- Гиперссылки — теряются в TSV, достаются из копии через Sheets API.
- Даты — только через `parseRuDate`.
- Статус «Жду релиз» → нормализуй в «Жду релиза» (`normalizeStatus`).
- У каждой игры есть `slug` (уникальный URL-ключ, генерируется в `normalizeGames`).
- Игры у которых есть `steamAppId` — по нему строятся обложки и ссылки на Steam.
